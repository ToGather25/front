## B. 백엔드가 의도적으로 막아놓은 경계 — 전환이 아니라 재설계 필요

### B-1. 교적부 공개 화면 (`Gyojeokbu.jsx`, `/교적부`)

**현재 상태**: 로그인만 하면(관리자 여부 무관) 누구나 볼 수 있는 `/교적부` 화면이 `src/config/members.config.js`의 정적 데이터(이름/생년월일/휴대폰/이메일/주소/가족관계/출석기록/목회자 메모 등, 12명분 상세 PII)를 그대로 렌더링한다. `isAdmin`인 사용자에게만 "목회 메모" 섹션을 더 보여줄 뿐, 페이지 진입 자체는 일반 로그인 사용자도 가능하다.

**백엔드 확인 결과**: 백엔드에 실제 교적부 도메인(`MemberRegistry`)과 API(`GET /api/church/admin/members`, `GET /api/church/admin/members/{publicId}`)가 있지만, **`hasRole("CHURCH_ADMIN")`으로 엄격히 가드돼 있고, 이건 설계 문서에 명시된 의도적 결정이다**:

> `docs/member-registry-access-design.md` (백엔드 저장소)
> "PUBLIC / MEMBER: ❌ ... **프론트 교적부 페이지는 관리자 전용 화면으로 취급**"
> "PII 최소 노출: 교적부는 성도 개인정보 원장이다. 필요한 역할에게, 필요한 필드만 노출한다."

즉 백엔드 팀은 이미 "프론트의 `/교적부`는 관리자만 봐야 한다"고 결론 내렸는데, 지금 프론트 라우팅은 그 경계를 지키지 않고 있다. 이 상태로 그대로 실API에 연결하면 관리자가 아닌 로그인 사용자는 403을 받아 화면이 깨진다(2026-08-21 감사에서 이미 한 번 발견되어 이번 배치에서 제외된 이력 있음).

관리자 전용 관점에서 보면 이미 별도로 `MembersManage.jsx`(`/admin/members`)가 `memberService.js`를 통해 정상 연동돼 있다 — **즉 "교적부 데이터 자체"는 이미 백엔드 연동이 끝났고, 문제는 그 데이터를 공개 화면(`Gyojeokbu.jsx`)에서도 보여주려는 프론트 쪽 설계**다.

**결론 — 단순 전환 불가, 세 갈래 중 하나를 정책적으로 결정해야 함**:
1. `/교적부`를 관리자 전용 라우트로 바꾸고(`AdminGuard` 적용) `MembersManage.jsx`와 통합/대체한다.
2. `/교적부`를 완전히 없애고 마이페이지에 "내 교적 정보 보기"(본인 1건만, 신규 API 필요 — 아래 C-6)로 축소한다.
3. 지금처럼 일반 로그인 사용자에게도 열어두고 싶다면, 백엔드에 "부분 필드만 노출하는 별도 공개 조회 API" 신설을 요청해야 한다(이름/직분/구역/연락처 정도만, 가족관계·출석·메모 등 민감 필드 제외) — 이건 백엔드 설계 원칙(PII 최소 노출)과 정면으로 배치되므로 승인 가능성은 낮다.

어느 쪽이든 **먼저 정책을 정해야 착수 가능** — "그냥 연동"이 아니다.

## C. 백엔드에 도메인/필드 자체가 없음 — 신규 개발 필요

### C-1. 성경 읽기/쓰기 — 랭킹, 진도율, 저장한 구절

**현재 상태**: `BibleRead.jsx`/`BibleWrite.jsx` 모듈 스코프에 하드코딩된 상수가 다수 있다.

| 상수 | 용도 |
|---|---|
| `READ_NEIGHBORS`/`READ_TOTAL`(`BibleRead.jsx`), `WRITE_NEIGHBORS`/`WRITE_MONTHLY`/`WRITE_TOTAL`(`BibleWrite.jsx`) | "랭킹" 탭의 순위표 |
| `BOOK_PROGRESS_READ`/`BOOK_PROGRESS_WRITE` | "내 현황" 탭의 66권별 완독률 |
| `READ_STATUS_CONFIG`/`WRITE_STATUS_CONFIG` | "내 현황" 탭 상단 통계(총 읽은 절 수, 연속일수 등) |
| `MOCK_SAVED_VERSES` | "내 구절"(좋아요한 구절) — 실사용자 저장 데이터는 `savedVerses`/`completedVerses` React state에만 존재, **새로고침하면 사라짐** |
| `saveLastPosition`/`getLastPosition`(`src/utils/bibleReadingProgress.js`) | 마지막으로 읽던 위치 — `localStorage`에만 저장, 기기 간 동기화 안 됨 |

**백엔드 확인 결과**: 백엔드 도메인 패키지 목록(`auth/bulletin/contact/event/gallery/jubo/member/my/notice/praise/sermon/worship`)에 성경 관련 도메인이 전혀 없다. 성경 본문 자체(`src/data/bible.json`)는 별도 사유로 프론트 로컬 유지가 확정돼 있지만(외부 성경 API 키 대기), **읽기 진도·좋아요 구절·랭킹은 완전히 다른 문제** — 이건 사용자 활동 기록이라 성경 API와 무관하게 자체 도메인이 필요하다.

**결론 — 신규 백엔드 개발 필요**: 최소한 (1) 사용자별 읽기/필사 진행 기록(책·장·절, 시각), (2) 좋아요한 구절 저장, (3) 랭킹 집계(일간/월간/누적) 세 가지 하위 도메인이 필요하다. 지금 당장은 성경 API 자체가 보류 상태라 우선순위가 낮지만, "좋아요 구절이 새로고침하면 사라진다"는 점은 사용자에게 실제로 눈에 띄는 결함이라 성경 API 연동보다 먼저 논의할 만하다.

### C-2. 교회 리더십/섬기는 사람들 (`Staff.jsx`)

**현재 상태**: `church.config.js`의 `staff.{headPastor,clergy,elders,...}`를 그대로 렌더링(이름/직분/연락처/사진/약력).

**백엔드 확인 결과**: 대응 도메인 없음(교적부의 `role` 필드와는 무관 — 이건 "성도 명부"가 아니라 "공개 리더십 소개 페이지" 콘텐츠).

**결론**: 신규 도메인 필요. 우선순위는 낮음(자주 안 바뀌는 정적 소개 콘텐츠라 실무에서는 CMS 성격 API 하나로 충분할 수도 있음 — `church/notice`쪽의 범용 CMS 목록(`worship-guides`, `{id,title,content,orderNo}`)을 재활용할 여지 있음, 별도 검토 필요).

### C-3. 예배 시간표 구조화 필드 (`church.worshipSchedule`)

**현재 상태**: `ServiceBand.jsx`, `NoticeSection.jsx`, `WorshipInfo.jsx`, `Events.jsx`(주일예배 합성 일정 생성용) 4곳이 `church.worshipSchedule.{regular,departments}`(요일/시간/장소 구조)를 정적으로 읽는다.

**백엔드 확인 결과**: `GET/PUT /api/church/**/worship-guides`가 있지만 완전히 다른 모델(범용 CMS `{id,title,content,orderNo}` — 자유 텍스트 목록이지 요일/시간/장소로 구조화돼 있지 않음). 2026-08-21 감사에서 이미 이 불일치를 발견해 "구조화 필드 추가"를 백엔드에 요청하기로 하고 스킵한 이력이 있다(아직 반영 안 된 것으로 보임 — `worship-guides` 쪽 소스 재확인 결과 구조 변화 없음).

**결론**: 백엔드 필드 확장 요청이 필요하고, 요청은 이미 나가 있는 상태로 보인다. 승인/반영 여부만 확인하면 됨.

### C-4. 마이페이지 프로필 확장 필드

**현재 상태**: 이름/이메일은 로그인 응답(`FrontUser`)의 실데이터로 이미 교체했지만, `src/components/mypage/mockData.js`의 `MOCK_USER`가 여전히 갖고 있는 `phone`/`address`/`role`/`district`/`group`/`birthdate`/`registeredDate`/`baptismDate`는 `FrontUser`에 없는 필드라 그대로 남아있다. 같은 파일의 `MOCK_DEPT`(직분/부서/직책/구역/소그룹/임직일)와 `MOCK_GROUPS`(소속 모임 목록)도 `DeptTab.jsx`("소속" 탭)에서 로그인한 모든 사용자에게 동일하게 표시된다.

**결론**: 이 필드들만 별도로 백엔드에 "마이페이지 프로필 확장" 요청 필요(정확히는 위 C-6의 "내 교적 정보 보기"와 데이터 성격이 겹친다 — 직분/구역/소그룹은 교적부 필드이기도 함, 함께 설계하는 게 자연스럽다).

## D. 백엔드 기능은 있는데 화면이 아예 없음 (참고 — 이번 audit 범위 밖이지만 기록)

### D-1. 찬양 (Praise)

`GET /api/church/praises` + 관리자 CRUD 3종이 백엔드에 존재하지만, 프론트에는 이 기능을 위한 페이지/컴포넌트가 하나도 없다(공개·관리자 모두). Figma 시안도 없어서 화면 설계부터 시작해야 한다 — "로컬 데이터를 백엔드로 바꾸는" 문제가 아니라 "신규 기능 개발" 문제.

### D-2. 갤러리 관리자 CRUD 일부

공동체/사진 등록은 이미 연동됐지만, 공동체 삭제·공동체/사진 수정 API가 백엔드에 없다(2026-08-22 감사 확인). 화면에서 이 버튼들을 아예 제공하지 않는 것으로 이미 처리돼 있음 — 백엔드에 API가 추가되면 그때 프론트 작업.

## E. 의도적으로 프론트 전용으로 두는 게 맞는 데이터

이 항목들은 "아직 못 옮긴 것"이 아니라 **애초에 백엔드로 옮길 이유가 없는** 데이터다.

| 데이터 | 파일 | 이유 |
|---|---|---|
| 성경 책 이름/약어 매핑, 구약/신약 목록 | `bible.config.js` | 성경 66권 구성은 안 바뀌는 고정 참조 테이블(enum 성격). 교회마다 다를 수 없음. |
| 사이트 검색 키워드/단축 링크 | `search.config.js` | 프론트 라우트 경로(`to:`)에 1:1로 묶여 있어 백엔드가 값을 가져도 의미가 없음(라우트 구조 자체가 프론트 코드) |
| GNB 메뉴 구조 | `church.config.js`의 `nav` | `ChurchContext.jsx`에 이미 "nav는 프론트 전용 라우팅 구조라 API 응답과 병합하지 않고 항상 defaultConfig를 쓴다"고 명시된 아키텍처 결정 |
| 행사 카테고리 색상 매핑 | `events.config.js`의 `DEPARTMENT_STYLES` | 순수 프레젠테이션(Tailwind 클래스) — 카테고리 "목록" 자체(`EVENT_CATEGORIES`)는 F로 분류 |
| 예배구분 공유 상수 | `sermon.config.js`의 `SERVICE_TYPES` | 관리자 등록폼과 공개 검색 필터가 값을 공유해야 해서 프론트 상수로 고정한 것 — 백엔드는 이 값을 자유 문자열로만 받음(검증 안 함) |

**성경 마지막 읽은 위치**(`localStorage`, `bibleReadingProgress.js`)는 애매한 케이스라 별도로 적는다: 지금처럼 "이 브라우저에서 마지막으로 읽던 곳"이라면 로컬 저장이 오히려 자연스럽다. 다만 "다른 기기에서도 이어읽기"를 원한다면 C-1의 읽기 진행 도메인에 포함시켜야 한다.

## F. SaaS 확장 시점에 필요 (현재는 1교회 전용 배포라 저우선순위)

`church.config.js`에는 위에서 다룬 것 외에도 `vision`(교회 비전), `greeting`(인사말), `transportGuide`(차량운행 안내), `floorGuide`(층별 안내), `communities`(회원가입 시 소속 선택지), `parking`(주차 안내), `publicTransit`(대중교통 안내) 등이 더 있다. 이 필드들은 `/api/tenant` 응답에 아직 하나도 포함되어 있지 않다(현재 응답: `id/name/fax/tel/email/pastor/social/address/logoUrl/features/shortName/denomination`뿐).

`church.config.js` 파일 자체의 주석이 이 상태를 정확히 설명한다:

> "이 파일 자체가 이 배포(이 저장소)의 기본 교회 데이터(옥길교회)이기도 하다 — ChurchProvider는 위 API 호출이 실패해도(백엔드 미배포 등) 이 값을 그대로 보여준다. 즉 이 저장소를 그대로 배포하면 '옥길교회 프론트'로 동작한다."

즉 지금 이 저장소는 "옥길교회 전용 사이트"로 배포되는 게 목표이지 여러 교회가 함께 쓰는 멀티테넌트 SaaS가 아니다. 이 상태에서는 이 필드들을 백엔드로 옮길 실익이 크지 않다(교회가 하나뿐이라 config 파일 수정 = 배포이므로 사실상 백엔드 DB 수정과 운영 부담이 비슷함). **여러 교회가 각자 다른 값으로 온보딩하는 시점이 오면 그때 `/api/tenant` 응답 필드를 확장하는 게 맞다.**

## 우선순위 제안

1. **B-1 (정책 결정)** — 교적부를 어떤 방향으로 정리할지 먼저 결정. 결정 전까지는 지금 상태(정적 데이터 + 로그인만 게이트)를 유지하는 것이 실제 PII 노출 확대보다 안전하다.
2. **C-1 (성경 저장 구절 유실)** — 백엔드 신규 개발이 필요하지만, "좋아요 눌러도 새로고침하면 사라진다"는 사용자 체감 결함이 크므로 성경 랭킹/진도율보다 먼저 검토할 가치가 있음.
3. 나머지 C·D·F는 각자의 사이클에서 필요할 때 순서대로.
